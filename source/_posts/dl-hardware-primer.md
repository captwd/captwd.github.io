训练模型时，你会看到一堆数字：CPU 33%、GPU 46%、内存 85%、磁盘 2%。这些数字背后是一套物理结构在工作。这篇是一份"为深度学习而学"的硬件原理入门——不追踪某台机器的状态，只讲清 CPU、内存、磁盘、GPU 各自为什么长成这样，以及深度学习为什么把它们的特性放大。所有数字按典型消费级硬件给量级。

## 0. 世界观：延迟金字塔

整台计算机的本质是**一座为速度妥协容量的金字塔**：每往下一层，容量大约 ×10~1000，但速度慢 ×10~10000。

| 层级 | 延迟 | 量级 |
|---|---|---|
| 寄存器 | ~0.3ns | 字节级 |
| L1/L2 缓存 | 1~10ns | KB~MB |
| L3 共享缓存 | 10~40ns | 几十 MB |
| 内存 DRAM | ~100ns | GB 级 |
| NVMe SSD | ~0.1ms | TB 级 |
| 机械硬盘 | ~10ms | TB 级 |

换个"人类时间标尺"（把 1 个 CPU 周期放大成 1 秒），差距会非常直观：L1 命中 ≈ 4 秒，L3 ≈ 40 秒，内存 ≈ 5 分钟，SSD ≈ **3.5 天**，机械盘寻道 ≈ **9 个月**，跨洋网络 ≈ **14 年**。

**这就是一切优化故事的根源**：深度学习里"数据搬运"的花费往往超过"计算"本身，因为数据住在这座金字塔的不同楼层。

## 1. CPU：一台专为"延迟"优化的机器

### 1.1 核心内部

一个 CPU 核心是五段流水线：取指 → 解码 → 乱序调度 → 执行 → 写回，配套多级缓存：L1（32KB 指令 + 32KB 数据，每核私有，~4 周期）、L2（~1MB，~12 周期）、L3（几十 MB，全核共享，~40 周期）。

关键概念：**缓存行（cache line）64 字节，数据按整块搬运**——这就是"顺序访问快、跳跃访问慢"的物理根源。CPU 设计的全部魔法，都是在"预测并提前把数据搬到楼上"。

  <img src="/img/hw-cpu-core.svg" alt="CPU 核心结构">
  <figcaption>CPU 核心：五段流水线 + 乱序执行 + 多级缓存（频率远不代表性能）</figcaption>
</figure>

### 1.2 四个决定性能的词

| 概念 | 原理 | 对训练的含义 |
|---|---|---|
| 频率 GHz | 每秒时钟节拍；节拍 ≠ 完成一条指令 | 笔记本会按温度/负载动态升降（throttling） |
| IPC × 频率 × 核数 | 性能三者缺一不可 | Python 循环 IPC 很低，主进程"忙"但产出少 |
| SMT 超线程 | 一个物理核伪装成 2 个逻辑线程 | 16 线程 = 8 物理核；33% 利用率 ≈ 5 线程真在干活 |
| SIMD 向量 | 一条 AVX 指令处理 8~16 个浮点 | NumPy/torch 的 CPU 算子靠它加速 |

### 1.3 "CPU 利用率 33%" 到底在量什么

操作系统每秒采样数百次，统计"**有任务可跑的核心·时间 ÷ 总核心·时间**"。所以 33% 的意思是：采样时刻平均只有 1/3 的核心有活干。它**不衡量这些活的含金量**（一个忙等循环也能 100%）。深度学习训练里 CPU 大部分等待来自：**等 GPU 同步、等数据、等锁（GIL）**。

## 2. 内存：工作台与虚拟内存的戏法

### 2.1 物理本质

每比特是一个**微型电容**（有电=1，没电=0）。电容会漏电，所以每隔约 64ms 必须整行刷新——这就是"易失性"和断电丢数据的由来。带宽 = 频率 × 位宽 × 通道数（DDR5-5600 双通道 ≈ 89GB/s）。

### 2.2 虚拟内存

程序看到的地址是假的：进程有独立的虚拟地址空间，MMU + TLB 负责翻译成物理地址。

- TLB 命中 → 翻译 ~1 周期
- TLB 未中 → 查页表（多次访存）
- 缺页（Major）→ 读磁盘（ms 级）

**换页（swap/pagefile）**：内存吃紧时，系统把冷页写回磁盘腾地方——之后每次访问都慢 10⁵ 倍。"内存不足"的真实过程就是：分配失败/换页 → 冷页写盘 → 任务管理器里"已提交"飙升。

  <figcaption>虚拟内存：MMU + TLB 翻译、缺页异常、页缓存与换页</figcaption>

### 2.3 页缓存：为什么第二次读文件几乎不花时间

OS 会把读写过的文件内容**自动留在空闲内存**里（Windows 叫 standby list，Linux 叫 page cache）。这是"空闲内存的聪明用法"，需要时立刻让位。数据集第一次读进内存后，之后每个 epoch 都是纯内存命中——这就是"读一次数据，整晚训练磁盘都退休"的原理。

### 2.4 锁页内存（pinned）

普通内存可能被换出，DMA 引擎不敢直接拿它做异步拷贝（数据可能中途消失）。**锁页内存 = 向 OS 承诺"绝不换出"**，于是 GPU 的 DMA 可以安全异步直读。PyTorch 的 `pin_memory=True` 就是在干这个。代价是锁死的页会**加剧**内存压力（不能当缓存用），一把双刃剑。

## 3. 磁盘：SSD 的"改写为什么这么麻烦"

### 3.1 机械盘 vs 固态盘

| | HDD | SSD |
|---|---|---|
| 介质 | 磁性盘片 + 磁头机械寻道 | NAND 闪存（电子囚禁在浮栅） |
| 随机访问 | 5~10ms（机械运动！） | 0.02~0.1ms |
| 顺序带宽 | 150~250MB/s（SATA） | NVMe 2~7GB/s |
| 寿命 | 机械磨损 | 每单元擦写次数有限（TLC ~1000-3000 次） |

### 3.2 NAND 的两个别扭特性（SSD 一切怪行为的根源）

1. **读/写按"页"（4~16KB）**
2. **擦除按"块"（= 几百个页一起）**

同一页要写第二次，必须先擦掉整个块。于是 SSD 内部有个"翻译官" **FTL（闪存转换层）**：

```text
你改写 4KB → 不敢原地擦（要拖上几百页）
  → 把新数据写到别的空页，改映射表
  → 旧页标记垃圾，攒多了后台回收（GC）
  → 副作用：写入放大（实际写 > 你写的）、掉速
  → 磨损均衡：FTL 故意把擦写摊到全盘所有块
```

"SSD 写多了变慢"和"寿命"都源于此。

  <img src="/img/hw-nand-ftl.svg" alt="NAND 页块模型与 FTL">
  <figcaption>NAND 的页/块模型与 FTL：写入放大、垃圾回收与磨损均衡的根源</figcaption>
</figure>

### 3.3 NVMe 比 SATA 快在哪

SATA/AHCI 只有 **1 条命令队列、深度 32**；NVMe 走 PCIe 直连，支持 **64000 条队列、每条 64000 深**——并行度差三个数量级。训练的启示：checkpoint 是大块顺序写（NVMe 强项）；数据集尽量顺序大块读，别每条样本一次小 IO。

## 4. GPU：一台专为"吞吐量"优化的机器

### 4.1 哲学差异

| | CPU（4 个教授） | GPU（一个礼堂的学生） |
|---|---|---|
| 核心 | 少量超强核心、乱序、分支预测、大缓存 | 几千个简单核心 |
| 目标 | 单任务**延迟**最小 | 总**吞吐量**最大 |
| 擅长 | 复杂逻辑、分支、串行依赖 | 海量同构小计算（矩阵乘法！） |
| 弱点 | 并行任务多时启动开销高 | 分支发散即空转 |

神经网络训练 = 巨量矩阵乘 = GPU 主场；Python 循环、数据整理 = CPU 主场。

### 4.2 SM、warp 与延迟隐藏

GPU 的最小调度单位是 **warp（32 个线程绑在一起，SIMT）**。每个 SM 同时驻留几十个 warp；当一个 warp 在等显存数据（几百周期）时，调度器**立刻切到另一个就绪 warp** 继续算——用海量切换把访存延迟藏起来，这叫**延迟隐藏**，是 GPU 编程的灵魂。

推论：如果驻留的 warp 太少（**occupancy 低**，比如 batch 只有 32），没有"备胎 warp"可切，GPU 只能干等 → 利用率低。这就是"小 batch 喂不饱 GPU"的架构层解释。

显存侧同样分层：寄存器 → 共享内存/L1 → L2 → GDDR/HBM（~300+GB/s，几百周期）。访存连续（coalesced）时带宽才能打满——张量的内存布局之所以重要就在这。

### 4.3 拷贝引擎：让"搬家"和"计算"同时进行

GPU 里有独立的 **DMA 拷贝引擎**，所以"上一批在算"和"下一批在拷"可以并行——这就是数据预取（prefetch）能提高 GPU 利用率的硬件基础。前提：源内存必须 pinned。

## 5. 串起来：一次 H2D 拷贝的完整旅程

以 `batch.to(device)` 这一行为例：

```text
① Python 调用
② PyTorch C++ 层把张量指针交给驱动
③ 驱动向 GPU 拷贝引擎提交 DMA 命令
④ PCIe 传输（数据须来自 pinned 页，否则先要 CPU 搬运 staging）
⑤ 拷贝完成触发中断
⑥ 驱动通知 CUDA 流"事件完成"
⑦ 同流里的后续 kernel 才开始执行
```

| 环节 | 参与硬件 | 典型耗时 |
|---|---|---|
| 命令提交 | CPU + 系统调用 + 驱动 | ~10µs 级（每次发射的固定开销） |
| PCIe 传输 | DMA 引擎 + PCIe | 毫秒级（几 MB ÷ 16GB/s） |
| kernel 计算 | SM 阵列 | 视模型，毫秒~几十毫秒 |

**全局图景**：训练就是在"延迟阶梯"上反复搬数据，同时让 GPU 的吞吐机器别停。你做过的每个优化都能在这张地图上找到坐标——**把数据搬到离计算最近的一层，或者让搬运与计算重叠**。
