换骨干实验怎么做才公平：MCD 标定、协议统一与配对检验

发表于2026-09-11|更新于2026-09-17|Matcha-TTS
|浏览量:

系列 · Matcha-TTS 训练手记 ｜ 目录 ｜ 上一篇：双向 Mamba2 集成

前两篇把 Mamba 换进了 Matcha-TTS，但”换成功”和”能下结论”是两回事。这一篇记录做对比实验时踩过的三个方法论问题：代理指标骗人、协议不统一、以及调度器和骨干混在一起没法归因。

一、先把指标的口径搞清楚

评估用的是三个指标：MCD（mel 倒谱失真）、WER / CER（ASR 转写的词/字错误率）。每个都有陷阱。

MCD 的绝对数值没有普适意义

自研的 MCD 提取器（log-mel 80 + DCT + DTW 对齐）和论文里常用的 SPTK-mcep 量纲不同，所以要做同体系标定：

参照点 数值 含义
声码器往返（真实 mel → wav → 声码器 → mel） ~3.65 dB 链路无损的理论下限
已训模型 ~51–53 dB 当前水平
跨语句自然语音对照 ~55–90 dB 超过这个量级说明细节已经很糊

所以”51.58 比 52.88 好”要在同一提取器下说，不能跨论文比绝对值。

WER 有天花板，会压缩差异

用 wav2vec2 做 ASR 时，真实语音本身转写就有错（这个叫 GT-WER）。我们的 val 100 句 GT-WER = 7.6%，意味着合成语音的 WER 最好也就能压到 7.6% 附近；当几个系统的 WER 都在 9% 上下时，差异空间本身只有 1 个多百分点，WER 不显著 ≠ 没有变好，很可能是天花板效应。

二、被代理指标骗过的一次

训练过程中每个验证点会算一个 val_mcd，但它是只取 2 条样本的快速代理。看那条曲线，后期一直在 56–59dB 徘徊，一度让人以为”这版骨干不行”。

结果跑完整的 100 句评估：

指标 训练时代理（2 句） 全量评估（100 句）
MCD 56.8 – 59.4 51.70

差了 5dB 以上，方向都反了。教训很直接：

  • 代理指标只能看趋势，不能用来选型或下结论
  • 样本量太小时 MCD 的方差极大（不同句子本身的 MCD 差异就很大）
  • 训练日志里的指标要注明样本量和用途，别和正式评估数字混在一张表里

三、协议不统一，等于没比

早期实验里不同系统用了不同声码器（BigVGAN / HiFi-GAN）、不同去噪开关，表格里数字混着放。虽然此前做过双骨干等价性验证（同 checkpoint 换声码器的逐句差异不显著），但要拿来做最终结论，协议必须统一。

最终定版：HiFi-GAN T2 + Denoiser（原论文配方）+ val 全量 100 句 + ODE 10 步，所有系统同一个流程。

统一协议后还做了一件事：把最强的对照组按新协议重评。之前那个”衰减 LR 的 ConvNeXt”最佳点只有 no-deno 的数字，于是用同一个 HiFi-GAN + Denoiser 重跑了一遍，避免”系统 A 挂 denoiser、系统 B 不挂”的隐性偏差。

四、用配对检验，而不是只看均值

100 句评估会逐句导出 CSV（mcd / wer / cer / 长度），这让我们可以做逐句配对的 Wilcoxon 符号秩检验——比只比平均值严谨得多，因为它消掉了”句子难度”这一项方差。

最终三系统同协议结果：

系统 MCD (dtw) WER CER
U-Net ep140（恒定 LR） 52.85 ±17.16 9.3% 2.5%
ConvNeXt V2（衰减 LR，最强对照） 50.88 ±16.22 10.4% 2.6%
双向 Mamba2 ep139（衰减 LR） 51.70 ±17.36 8.7% 2.3%

逐句配对 Wilcoxon（n=100）：

对比 MCD Δ p WER Δ p CER Δ p
Mamba vs U-Net（恒定 LR） −1.16 0.0015 −0.6pt 0.30 −0.2pt 0.67
Mamba vs ConvNeXt（衰减 LR，最强对照） +0.82 0.23 −1.7pt 0.023 −0.3pt 0.29

这张表能读出的、能写的结论：

  1. 对上最强对照，MCD 是打平（+0.82，p=0.23 不显著），WER 是显著更优（p=0.023）
  2. 对上恒定 LR 的基线，MCD 显著改善，但这个改善里含有 LR 衰减的贡献（见下节）

五、混进了调度器：一个必须承认的混淆变量

Mamba 那条 run 从一开始就挂了 LR 阶梯衰减（1e-4 → 6.25e-6），而 U-Net 基线是恒定 LR 训的。所以 “Mamba vs U-Net 的 −1.16dB” 不能全算在骨干头上。

更早的对照实验已经量化过纯调度分量：同一条 U-Net 加衰减后，ep135 的 MCD 从 54.4 掉到 51.0 左右（配对 p<0.0001）。也就是说，衰减单独就能贡献 1dB 量级。

剥离混淆后的诚实表述应该是：

在同等调度与评估协议下，双向 Mamba2 骨干与最强的衰减 ConvNeXt 配置在 MCD 上持平，在 WER 上显著更优；同时参数量只增加 3%、复杂度线性。

要彻底把”骨干”和”调度”分离，还差一个对照：恒定 LR 的 Mamba run。如果它像 U-Net 恒定 LR 一样震荡到 55+，那就同时证明了（1）震荡是调度问题不是骨干问题，（2）骨干差异的干净读数。（这条对照就是下一步。）

六、顺带记录一个调度器坑

MultiStepLR 在恢复训练时很容易静默失效：仓库在 resume 时会把 scheduler 的步数计数器拨到 恢复 epoch - 1，如果你把里程碑按”本 run 的局部 epoch”写（比如 [5, 15, 25, 35]），而恢复点是 epoch 99，那这些里程碑永远够不到，全程就是恒定学习率——而且不报错。表现就是”衰减实验悄悄变回了恒定 LR 实验”。

规避：

  • 里程碑一律写在全局 epoch 轴上（[105, 115, 125, 135]）
  • 训练中途抽查 checkpoint 里的 lr，确认调度真的生效

小结

换骨干这类实验，想让结论站得住，基本就是这几条：

  1. 统一协议：同一批评估数据、同一声码器、同一去噪设置、同一步数
  2. 把最强的那组对照也按新协议重评一遍，别让它停在旧协议下
  3. 代理指标只看趋势，别拿小样本量的代理去下结论
  4. 逐句配对检验，而不是比均值
  5. 控制调度这类混淆变量：要么两组同调度，要么写清楚”这部分增益里有多少来自调度”
  6. 指标已经贴着上限时，如实说”不显著”，比硬凑一个”更好”更可信

三篇下来，环境、集成、评估这条线就闭合了。代码、配置和评估脚本都在仓库里，欢迎复现和指正。
