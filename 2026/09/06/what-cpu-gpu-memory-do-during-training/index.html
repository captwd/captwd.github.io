训练时 CPU、内存、磁盘、GPU 都在干什么：一次实测画面的逐项解读

发表于2026-09-06|更新于2026-09-11|深度学习实践
|浏览量:

系列 · Matcha-TTS 训练手记 ｜ 目录 ｜ 上一篇：硬件原理入门 ｜ 下一篇：PyTorch 参数解剖

上一篇讲了原理，这一篇是应用：拿一次真实训练的监测画面，逐项解释每个数字背后的流水线状态。画面快照（Windows 训练、有效 batch 64 时代）：

配套的流水线是：离线预处理缓存 + 梯度累积 + num_workers + pinned memory + 每 epoch 存 258MB checkpoint。结论先给：瓶颈不是某个设备的算力，而是”链路延迟”——四部件都半闲。

1. 一条数据的完整旅程

能量在内存里循环，磁盘基本退休。

2. CPU 33%：在当”指挥”而不是”工人”

角色 具体工作 特征
主进程（GIL 单线程） Lightning hook 链调度；把 loss.backward() 拆成几百个 kernel 并发射进 CUDA 流；日志/进度条；每 step 与 GPU 同步 一个核心常驻忙
dataloader worker ×2 读页缓存 .npy → collate（变长序列 pad 成 batch）→ pickle → 经共享内存交主进程；预取下一批 两个核心间歇忙，与主进程重叠
验证期尖峰（每 5 epoch） matplotlib 光栅化画图、DTW-MCD 的 numpy 循环、tensorboard 写盘 短时冲高，别误判成泄漏

为什么 33% CPU 喂不饱 46% 的 GPU：GPU 每步要等”主进程发射完 + 数据到位”。串行依赖链上任何一环等待，GPU 就空转。两边等待的是同一份时间——瓶颈是链路，不是某个设备的算力。

3. 内存 85%：四类住户 + 一个危险的舞伴

住户 大小（实测/估） 性质
主进程 python ~2-3GB torch 库本体 + CUDA 主机端 + 缓存对象
worker ×2 ~1.6GB（各 780MB） 每个 worker 都 import torch 并持有数据集引用
页缓存（standby list） 弹性，可达数 GB 好内存，需要时可立即让位
其它应用 视情况 浏览器硬件加速还占显存，双重挤压

85% 为什么是警戒位：此前 batch 64 时，显存溢出约 1GB 被塞进”共享 GPU 内存”（也就是这份系统内存）。85% + 1GB 会顶到换页阈值，系统开始把页缓存放出去换空间，连累 worker 读数据变慢，形成”GPU 等数据 → CPU 等内存”的连锁。换成 batch 32 + 梯度累积后两个问题一起消失——这就是”一石二鸟”的机制解释。

自查方法：任务管理器 → 详细信息 → 按内存排序，能看到多个 python.exe（主 + worker）；”性能 → 内存”里”已缓存”那栏是页缓存，不计入”使用中”。

4. 磁盘 2%：被缓存架构”退休”的部件

动作 频率 流量 为什么感知不到
读训练数据 首轮 epoch 几个 GB 首轮后驻留页缓存，后续纯内存命中
写 checkpoint 每 epoch 1 次 258MB NVMe 顺序写 GB/s 级，0.2 秒写完，摊到整个 epoch ≈ 1MB/s
tensorboard 事件 持续 KB 级 OS 写缓冲聚合

这正是离线预处理缓存的红利：磁盘从”持续工作部件”变成只负责 checkpoint 的”仓库管理员”。如果删掉缓存重训一轮，你会看到磁盘常年 10-30%、CPU 多一摊 mel 计算。

5. 流水线视角：瓶颈在哪，还有哪些杠杆

对 16M 级小模型 + 8GB 卡，这就是稳态；模型/批次变大后，链条会自然被计算压满。可选杠杆：

杠杆 预期收益 建议
加大 num_workers 批组装更快，GPU 等待略减 内存只剩 2.3GB 余量，每个 worker ~780MB，最多再 +1
提高 GPU 利用率 — 不是本机调参能解决的：需要更大模型/批次/序列
降低 checkpoint 频率 几乎无收益（磁盘不忙） 不动，每轮存档是血泪换来的保险
关浏览器等 GPU 应用 显存余量 +几百 MB 值得做

小结

  1. 看利用率别只看单个数字，要问”谁在等谁”——四个部件都半闲 = 链路延迟瓶颈
  2. 页缓存让磁盘”退休”，但它是借用的空闲内存：内存一紧就被收回，进而拖慢整条链
  3. 小模型训练的 GPU 利用率有”框架调度地板”，硬抠不如换更大的计算规模
